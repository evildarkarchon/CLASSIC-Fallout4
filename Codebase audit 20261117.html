CLASSIC codebase audit

17 November 2026 · branch classic-next at 0746c60c · read-only review, nothing was built or run · revised with the maintainer's decisions · one approved change made afterwards: the log corpora were sanitised (T19)

The codebase is in good shape where it has been deliberately designed: the scan-run contract, durable publication, User Settings, and the conformance gates are careful work. The problems cluster in three places: older scan-engine code that predates those contracts, GUI lifecycle paths that no test exercises, and Python-era leftovers in support crates, docs, and the repository itself. Seven findings are rated high because they produce wrong behaviour for ordinary users today.

Summary

How much to trust each finding. Five reviewers each read one area of the code; I then re-read the cited code for every high-severity finding and a sample of the rest. Each finding carries one of three labels:

  • Re-verified: I read the cited lines myself and the claim holds.
  • Reviewer-traced: a reviewer read and traced the code; I did not re-check it.
  • Probable: the mechanism was read, but the trigger or consequence was not confirmed. The finding says what would settle it.

Nothing was executed through cargo or the build wrappers. Corpus statistics (for example "32 of 1,013 sample logs") come from a reviewer's Python emulation of the Rust logic over sample_logs/, not from the engine itself.

All findings

Strengths worth keeping

  • The scan-run contract makes invalid requests unrepresentable. Targeted runs cannot request log movement and FCX cannot be requested without setup context, both pinned by compile_fail doctests (scan_run/contract.rs:184-234).
  • classic-durable-publication is well built. Same-directory staging, sync_all before the move, write-through MoveFileEx, durability uncertainty returned as a value, and one lock shared by install, rollback, and settings.
  • Update consent is bound to bytes. The approved update carries the tag and per-file SHA; apply re-fetches and rejects drift before touching disk. Asset URLs are pinned by scheme, host, owner, repo, tag, and decoded asset name.
  • User Settings fail closed. Malformed documents block commits while retaining the bytes, commits re-check the revision under the lock, and migration writes a verified content-addressed backup.
  • SQL identifier handling is complete. validate_table_identifier runs before every interpolation in pool_sqlx.rs, and all values are bound.
  • The gates test themselves. The workflow policy pins each gate step's command, order, runner, and timeout, and its tests delete, reorder, and weaken steps to prove the check fails.
  • Runtime discipline holds. One LazyLock<Runtime>, enforced by clippy.toml; across 284 production Rust files there are about 100 unwrap/expect calls, no todo!, and one unsafe block outside the FFI boundary.
  • The FFI observer contract is typed. The observer is noexcept, delivery failure is a typed value under a Rust-applied policy, and out-of-range shared enums are rejected before a run starts.
  • CLI robustness. Ctrl+C sets an atomic that a monitor thread relays to Rust, prompting is gated on an interactive stdin, and exit codes are distinct (0, 1, 2, 130).

Method and limits

What was done. A mechanical pass over the whole workspace (lint configuration, dependency duplication, panic and unsafe sites, CI shape, tracked-file hygiene), then five parallel read-only reviews: the scan pipeline; config, update, and settings; foundation and support crates; frontends and the CXX bridge; tooling, CI, and docs. I then re-read the code behind every high-severity finding and a sample of medium and low ones.

What was not read. Roughly 114,000 lines of Rust and 30,000 of C++ are tracked; the reviewers read the large and central files fully and skimmed or skipped the rest. Not reached, among others: scan_run/contract.rs lines 560-770 and 1610-2170, analyzer.rs, fcx_handler.rs; explicit_yaml_data.rs and most of classic-user-settings-core beyond commit, migration, and document; most classic-scangame-core checkers (ba2.rs, unpacked.rs, wrye.rs, enb.rs, and others); the TUI's scan_run.rs, ui.rs, and tabs; the rest of xtask/src/conformance/ and cxx_bridge_gate/. Test files were mostly grepped, not read. Absence of findings in those files is not evidence they are clean.

What changed in the repository. The audit itself changed nothing. Afterwards, with the maintainer's approval, the tracked log corpora were sanitised (T19): 896 sample logs renamed, 136 path occurrences masked in 16 files, and one doc line updated. Those changes are committed locally as b0a4188f and not pushed. Line numbers in findings refer to source files at 0746c60c, which that commit did not touch.

What was not done. No build, test, clippy, or benchmark run; no GitHub API calls; no dynamic confirmation of any bug. Performance findings state mechanisms, not measured speedups. The Qt null-pointer consequence in G2 and the glob behaviour in S3 follow from library semantics and were not executed.

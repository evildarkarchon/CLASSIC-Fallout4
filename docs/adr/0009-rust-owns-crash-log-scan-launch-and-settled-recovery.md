# Rust owns Crash Log Scan Launch and settled recovery

Crash Log Scan Launch lives behind one read-only Rust interface so CLI, GUI, TUI, Node, Python, and C++ adapters do not each turn saved User Settings, the selected game, and per-run overrides into a Crash Log Scan Run request. One operation takes the Installation Root, a Standard or Targeted scan intent, and optional per-run overrides, and returns the Crash Log Scan Run request, the Crash Log Scan Setup Context when FCX Mode is enabled, and typed launch diagnostics rendered as Display Content. A supplied override always wins over the saved value; when the target game differs from the managed game, the saved game-specific values are not applied and each one not applied is reported; a Standard scan's base folder is always the Installation Root; and degraded User Settings produce a scannable request from defaults plus the User Settings diagnostics rather than an error. The rules it consumes keep their own owners: User Settings decides which FormID database rows apply to a game, so Fallout 4 VR shares the Fallout 4 rows the way it already shares the Main database and YAML Data; Config locates the Installation Root from one candidate list with no silent fallback; and the Crash Log Scan Run Display Content module renders launch diagnostics and the recovery prompt. This supersedes the clause of ADR-0002 assigning typed request projection to adapters; event and result mapping, user messaging outside the run's own prose, and the rest of that decision stand unchanged.

The launch interface never persists anything. It opens User Settings read-only, so the rule that a User Settings Update must be accepted before it is committed still holds, and a frontend that wants to save a path or destination does so as its own explicit User Settings Update before or apart from launching. It sits in its own business-logic module above both User Settings and scanlog core, so scanlog core stays unaware of User Settings as the Crash Log Scan Setup Context definition requires. The split is drawn here because request projection was the one launch-time rule with no owner: five adapters each rebuilt it, and they drifted on which FormID databases a Fallout 4 VR scan uses, where a Standard scan looks for Crash Logs, which folder is the Installation Root, whether FCX setup facts include the XSE log, and whether a settings document needing migration can scan at all. A rule with no owner cannot be fixed once, and the GUI's copy could only be tested by reading its source text.

The Local Ignore recovery continuation is exposed as a pending recovery and settled, rather than carried as an optional field and passed to separate resume and abandon entry points. A run result offers an optional pending recovery that bundles the single-use continuation, the recovery prompt already rendered as Display Content, and whether cancellation was already requested, so a frontend told the run is cancelled does not prompt. The frontend settles it with an optional Local Ignore Recovery Decision, where no decision means abandon with the existing semantics: cancel, then finish as cancelled after discovery with no filesystem work. Settling returns a settled result type that carries no continuation, so a second recovery request and a recovery status without a continuation are unrepresentable, and the defensive branches every adapter wrote for them go away. Execution takes a policy saying whether failure to deliver an observer event cancels the run, run results report that delivery failed, and a delivery failure before a pending recovery means Rust abandons that recovery instead of dropping it. Single-use consumption, the typed consumed-continuation failure on replay, the non-interruptible Reset To Default transaction, and resuming without rediscovery from ADR-0002 and ADR-0006 are unchanged. Settling without a decision is the one abandonment operation ADR-0007 called for; the Local Ignore Recovery Decisions remain exactly two, and abandonment is still not a third decision. The separate resume and abandon entry points, the execution has-continuation and take-continuation accessors, and the optional continuation field are removed on every surface with no deprecated aliases, and the parity gates assert their absence.

A prompter callback, in which Rust calls back into the frontend to obtain the decision mid-run, was considered and rejected. The C++ bridge is synchronous and its observers are `noexcept`, so a callback that waits for a user would have to cross the bridge in the other direction and carry failure back through it. The TUI is a non-blocking state machine on the single shared Tokio runtime, so a callback would block a runtime worker thread for as long as a dialog stays open. The GUI already marshals its prompt with a blocking queued connection from a worker thread, and the Node and Python CLIs treat recovery as terminal. A settled continuation fits every one of those shapes: each adapter executes, checks for a pending recovery, lays out the prompt, and settles with the user's choice on whatever thread and schedule it already uses. This record exists so the callback design is not re-proposed without that context.

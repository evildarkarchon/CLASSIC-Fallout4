# Version Registry remaining query conformance

Issue #213 extends the common `version-registry` pack with enumeration, game/mode filtering, XSE configuration, and crash-generator list and selected-configuration queries. Both CXX namespaces execute their public enumeration, XSE, and crash-generator entry points; the promoted namespace also executes its filtered query. Rust, Node, and Python observe the same fixture-owned metadata. Missing IDs, missing optional configuration, and missing crash-generator versions remain explicit successful absence outcomes.

The separate `version-registry-details` pack requires Rust, Node, and Python. CXX has no matching extended query surface. It observes exact-version and short-name lookup, correct/wrong mode selection, address-library resolution, crash-generator version strings, executable and script hashes, unknown-version policy/defaults, compatibility, and the filtered Node snapshot. Invalid version input produces an attributed parse error, distinct from empty successful queries. Collection sorting only normalizes unordered hash sets or maps; all returned values come from the native APIs.

Every scenario writes identical authored YAML to a temporary directory before first access. Dedicated participant processes isolate the singleton's first initialization. Each receipt inventories the original `CLASSIC Main.yaml` bytes, so unrequested writes or disappearance fail comparison. The richer seed includes one real extender configuration and one crash-generator configuration; absence cases reuse that same registry.

Coverage predicates name actual operations. Common metadata lookup cannot prove extended query methods, and extended queries cannot prove enumeration or matching. Known complementary methods in `operation_scope.py` remain assigned to their other executable pack. Python's constructor is invoked for each scenario and its module-level matching helper is compared with class matching. Existing source/type checks, negative analyzers, and unrelated local tests remain in place. No public API signatures or behavior change.

The source-backed Node contract now attributes the extended exports to their actual Rust crate and methods, preserving mapping IDs and the retained runtime registry. Declaring the owner alone does not grant coverage: receipts must satisfy the operation-specific family predicates.

`version-registry-values` separately executes the Python model methods and their Rust core contracts. Its capability names `CompatibleRange`, `get_compatible_crashgens`, and `is_compatible_with`, selecting only Rust and Python. Source-backed method mappings replace aggregate Python model mappings, so exact method paths grant coverage without enrolling every adapter that transports a shared DTO. The common pack additionally compares the Python model's selected crash-generator method with the registry method, and the details pack compares their version-string methods. Observations include inclusive range boundaries, model and crash-generator compatibility, default selection, and the Python ID equality/hash behavior. Hash bytes never enter expected data. Equality/hash observations strengthen the check but do not claim a Rust model equality/hash API that does not exist; their original binding tests and metadata remain retained.
